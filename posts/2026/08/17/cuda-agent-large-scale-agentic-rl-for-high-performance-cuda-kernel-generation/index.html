CUDA Agent: Large-Scale Agentic RL for High-Performance CUDA Kernel Generation

Fyw0o Nothing•2026-08-17AI4SEpapers

arxiv_link

Core Terminologies

  • TVM：一个开源机器学习编译框架，比torch.compile更像一个可显示调度和自动调优的“编译器研究平台”

motivation

  1. 通用 LLM 的 CUDA 优化能力不足：作者指出，通用模型虽可生成程序，但在 CUDA kernel 生成上仍不具备与 torch.compile 竞争的性能，根因是高性能 CUDA 所需的硬件与 profile 知识高度专门化。
  2. training-free受模型基础能力限制：若基础模型不具备足够的cuda代码与优化只是，收益受限
  3. 多轮迭代浪费上下文并限制策略自主性：上下文会保留大量已失效的信息；agent的行为被固定模板限制，每一轮都要求“基于上一版代码修复”，因此模型通常只能做局部编辑。
  4. 长程CUDA RL不稳定：CUDA token在通用预料中极罕见，低概率token与训练/推理精度差异会导致PPO重要性采样比剧烈波动

Contributions

  1. CUDA Agentic RL，提出 CUDA Agent，组合可扩展数据合成、带技能的 CUDA 开发环境，以及面向长上下文、多轮训练稳定性的 RL 技术
  2. 在 KernelBench 上报告相对 torch.compile 的 Level-1、Level-2、Level-3 Faster Rate 分别为 100%、100%、92%；论文称其在该设置下优于所比较的专有模型

WorkFlow

构造训练任务

  1. 先从torch和transformers中挖掘已有的pytorch算子类，但是不能只训练这种单算子，agent容易学到局部kernel，却少见真实场景的跨算子融合的机会
  2. 用LLM从种子库中抽取最多5个兼容算子，组合成一个新的pytorch参考模型
  3. 得到一个新的训练任务：
输入：pytorch参考的模型代码，模型参数，随机输入生成器
目标：实现model_new.py与自定义CUDA/C++扩展
约束：输出与该模型一直，尽量快于torch.compile
  1. 最后只保留可作为RL环境的任务

CUDA Agent rollout with tools

把cuda编码特定的指令和工具以agent skills呈现

核心机制：

  1. 使用提供的profill脚本分析模型实现的性能，识别瓶颈和优化机会
  2. 重写model_new.py并开发响应的cude kernel和自定义算子
  3. 在提供的GPU沙箱环境中编译和评估，若未达标则继续迭代

更加鲁棒的RL奖励机制

作者发现现有的方法例如使用相对与基线的加速作为奖励信号，例如：运行失败负值，运行成功用与基线速度的比值作为奖励。这种方法存在异常值，并且偏向于简单的内核

为了解决这个问题，作者提出了更加鲁棒的奖励机制，联合正确性和执行延迟：奖励为 \(\{-1,1,2,3\}\)：错误为 -1；正确但未达加速门槛为 1；比 eager 快超过 5% 为 2；同时比 eager 与 compile 快超过 5% 为 3。

在后面的实验验证了这一奖励机制的有效性

稳定的RL训练算法的改进

作者在最初的RL训练的时候只能稳定训练到17步然后模型就会崩溃，分析具体的原因：源于严重的领域分布不匹配，也就是说模型的预训练语料库中缺少cuda方面的知识，这种分布差距导致采样到许多低概率的cuda内核代码token

为了实现稳定的强化学习，提出了一个简单而有效的预热策略：使用经过单轮RL后的基础模型生成的智能体轨迹来初始化模型

单轮 PPO 预热：

  • 输入 (Input)：基础模型 Seed1.6 与任务集。
  • 核心机制 (Mechanism)：先在单轮 CUDA 生成上执行 PPO，基础模型同时充当 policy 与 value network。
  • 输出 (Output)：具备初步 CUDA 生成能力的模型，用于采样真实多轮 agent 轨迹。

Actor/Critic 初始化与多轮 PPO

  • 输入 (Input)：预热后产生的多轮轨迹。
  • 核心机制 (Mechanism)：仅保留总奖励为正、且不包含冗余循环或非法工具调用模式的轨迹；用它们做 RFT 初始化 actor。随后以轨迹状态和最终奖励预训练 critic；最后采用 PPO 进行完整多轮 Agent RL。
  • 输出 (Output)：CUDA Agent 策略模型。论文称 RFT 抑制 actor 熵失控，value pretraining 避免 critic 无法评估中间状态而产生异常长轨迹。

experiments

  • 评估基准 (Benchmarks & Datasets)：KernelBench 的 250 个任务：Level-1 100 题、Level-2 100 题、Level-3 50 题。作者将原有单文件任务适配到自己的多文件 Agent 环境。训练使用 Seed1.6（23B active / 230B total MoE）；实验环境为 128 张 NVIDIA H20 GPU。 论文 4.1
  • 核心指标 (Evaluation Metrics)：
  • Pass Rate：生成 kernel 成功编译并通过数值正确性测试的比例。
  • Faster Rate：正确且快于 eager 或 torch.compile 基线的比例。
  • Speed-up：仅对正确结果计算的几何平均加速比。
  • 最终分数取每条 Agent 轨迹中、相对 torch.compile 加速最高的候选；它不是单次采样的 Pass@1。
  • 关键实验结果 (Main Findings)：以下为 Overall、相对 torch.compile 的结果。

| 模型 | Pass Rate | Faster Rate | Geomean Speed-up |<br> |---|---:|---:|---:|<br> | Seed1.6 基座 | 74.0% | 27.2% | 0.69× |<br> | GLM-4.6 | 75.6% | 19.2% | 0.57× |<br> | Kimi K2 | 66.8% | 22.8% | 0.66× |<br> | Gemini 3 Pro | 91.2% | 69.6% | 1.42× |<br> | Claude Opus 4.5 | 95.2% | 66.4% | 1.46× |<br> | CUDA Agent | 98.8% | 96.8% | 2.11× |

分级结果中，Level-2 的 Faster Rate 为 100%，相对 compile 的几何平均加速为 2.80×；Level-3 为 90% 和 1.52×。 论文表 1

  • 消融分析与洞察 (Ablations & Insights)：

| 变体 | Pass Rate | Faster Rate vs. Compile | Speed-up vs. Compile |<br> |---|---:|---:|---:|<br> | 去掉 Agent loop | 77.1% | 14.1% | 0.69× |<br> | 去掉稳健离散奖励 | 96.8% | 60.4% | 1.25× |<br> | 去掉 RFT | 95.6% | 49.8% | 1.05× |<br> | 去掉 Value Pretraining | 98.6% | 50.9% | 1.00× |<br> | 完整 CUDA Agent | 98.8% | 96.8% | 2.11× |

对于去掉 RFT 或 value pretraining 的变体，作者报告的是训练崩溃前最后一个验证点，而非相同训练预算后的稳定终点；因此这两行支持“稳定性相关”的结论，但并非完全对称的最终模型对比

Limitations & Future Work

  • 作者承认的局限 (Limitations)：
  • 未与 TVM 等更复杂的编译器框架比较。作者给出的理由是：这类框架的调优开销和部署复杂度使其难以纳入数千条 rollout 的 RL 循环。
  • 训练依赖大规模 GPU 池与进程级隔离，具有较高算力和工程成本，限制了复现可及性。
  • 论文证明了 Agent 在它们的环境中经常快过 torch.compile，但尚不能证明它也快过经过 TVM 自动调优后的实现。
  • 规划方向 (Future Directions)：
  • 原文明确提出的未来方向只有一项：探索资源效率更高的训练策略。
  • 原文没有承诺 TVM 集成、跨芯片评测、权重发布或特定产品化时间表。官方仓库目前明确发布的是 6K 数据集、SKILL.md 和 Agent 工作目录。 论文局限性 官方仓库

Critical Analysis

  • ADV：该工作真正可迁移的资产不是一个特定 kernel，而是“受控执行环境 + 可验证 reward + 长程轨迹训练”的闭环。对算子融合、代数化简、数据布局选择这类无法由纯文本质量判断的优化，执行延迟是比人工代码标签更直接的监督信号。这个范式可扩展到 Triton、HIP、通信 kernel 或端到端子图优化，但前提是能稳定定义正确性和性能 oracle。
  • DISADV
  • 性能并非只由 kernel 决定：分数在 H20、固定软件栈、固定形状与基线下产生；论文未给出跨 GPU 架构、跨驱动版本或跨形状分布的稳定性。一个在 H20 上较快的 tile、向量化宽度或库调用，未必迁移到 A100、H100、Blackwell 或 AMD GPU。
  • 正确性覆盖有限：训练环境用 5 组随机输入校验。这能排除常数输出和明显错误，但不能充分覆盖数值边界、非连续 tensor、不同 dtype、极端形状、NaN/Inf 传播和训练反向传播语义。
  • 分数掩盖搜索成本：评估允许最多 200 轮交互，并从轨迹中挑相对 torch.compile 最快的候选。该口径衡量“给定搜索预算下能否找到好 kernel”，不衡量首个可用 kernel 的质量，也未报告每个成功 kernel 的编译次数、GPU 小时、token 成本或 wall-clock 延迟。
  • 基线覆盖不足：torch.compile 是合理且常用的基线，但不是最强的全部编译优化系统。未比较 TVM、手工 CUTLASS/cuDNN 调优、以及面向具体算子的生产 kernel 库，限制了“超过编译器”的外推范围。
  • 去污染不等于语义独立：AST 相似度阈值可降低近似代码重合，却不能证明训练任务与测试任务在算子模式、代数变换、访存策略或库选择上完全独立。这是基准训练中常见的语义泄漏风险。
